# How to author a figure

Every diagram on this site is generated by `tools/gen_figures.py` from a short YAML file.
**You never write SVG, and you never edit a generated SVG, a generated paste block or
`docs/figure-conventions.md`.** If a figure is wrong, the spec is wrong or the generator is.

This page is the working procedure. The rules behind it are `R-FIGURE` in
`docs/plans/readability-guide.md` and report D (`docs/plans/readability/report-D.md`); the
tokens and the reader-facing legend are `data/figures/tokens.json` and
`docs/figure-conventions.md`.

## 1. Before you touch anything, read the page

Read the target step page **in full**, not just the section the figure goes into. You are
going to draw only what that page already says, so you need to know:

* what the step does, in the page's own words;
* which of its statements are public facts, which are this reference's reading, which are
  inferred and which are "typical practice";
* which numbers the page gives, and the footnote key beside each of them
  (`[^pdk-04]`, `[^pdk-03]`, …);
* where the page says something is **not public**.

A figure may never say more than its page does. The lint catches some of that; most of it
is your judgement.

## 2. Copy a spec that is close to yours

```
cp data/figures/iso-006-stie.yaml data/figures/<series>-<step>-<code>.yaml
```

The name is the figure's `id` and must match the file name: `<series>-<step>-<code>` for a
cross-section (`iso-006-stie`), `flow-*`, `tool-*`, `mask-*` or `chart-*` otherwise.

## 3. Fill in the fields

A cross-section spec (`kind: xsection`) has these and nothing else:

| Field | What goes in it |
|---|---|
| `id` | the file name without `.yaml` |
| `kind` | `xsection` |
| `page` | the path of the target page, from the repository root |
| `series` | the series file in `data/figures/`, e.g. `series-isolation.yaml` |
| `alt` | 60–450 characters describing the **geometry**: what a reader who cannot see the picture would need. No citations, no step codes to look up, no interpretation |
| `caption` | what is shown, the page's hedges **repeated**, the footnote keys, ending "Not to scale." |
| `arrow` | `title` (the step code and number) and `note` (one sentence saying what the step does), shown between the two panels |
| `panels` | two of them: "before" and "after" |

Each panel has:

| Field | What it does |
|---|---|
| `state_after` | the step number whose finished state this panel draws (`"005"`) |
| `title` | `Before: …` / `After: …`, a short sentence |
| `crop_depth` | how much substrate to draw below the surface; presentation only, it changes no geometry |
| `hide_layers` | layers to leave out of this panel (use it when the target page does not discuss an optional layer) |
| `hide_labels` | layers to draw but not label |
| `labels` | per-panel overrides of a series label |
| `highlight` | x ranges whose surface is traced in the accent colour: *the one thing this step changed* |
| `dims` | at most a couple: a dimension line with a label |
| `callouts` | a label on a feature that is open at the top (a trench, a hole, a polished surface) |
| `show_ions` | `false` to suppress the implant arrows of the step in this panel |

`dims` and `callouts` are labelled from **above**, in a band over the drawing, and there may
be **at most two of them per panel**. Everything else is labelled from the right-hand
column, automatically.

### Labels

Every label is `{title, note, basis, cite}`:

* `title` — a couple of words. No numbers.
* `note` — one short sentence. Naming a step (`step 004`, `steps 010, 011`) is free; **any
  other number needs `cite:`**.
* `basis` — `public`, `reading`, `inferred` or `typical`. Anything but `public` prints its
  tag in amber under the label, so use the one the page's own wording supports.
* `cite` — the footnote key, without the `[^…]`, and it **must already be defined on the
  target page**.

If a value is not public, say so first: `note: "not public; about 0.33 µm is this page's
reading"`, `basis: reading`. And never draw a value that is not public to scale.

**Nothing from a patent that `tools/check_inforce.py` treats as in force may appear in a
figure, in any form** — not a number, not a phrase, not the footnote key. A figure cannot
sit inside a collapsed note, so there is nowhere for it to go. The lint refuses the key.

### Series files

`data/figures/series-*.yaml` is one geometry for a whole module; a figure is a state of it.
**Adding a step to a series changes every figure of that module**, so a series file is
written once, by a stronger model, and fact-checked against every page it feeds. If your
figure needs a layer the series does not have, say so in your progress file rather than
editing the series on your own.

Series labels carry no numbers, because the same label appears on a dozen different pages
and each one would need the same footnote key. Numbers go in the per-figure `dims` and
`callouts`, where they can carry the key their own page defines.

## 4. Build

```
uv run python tools/gen_figures.py build data/figures/<id>.yaml
```

It writes `docs/_static/figures/<id>.svg`, `.light.svg` and `.dark.svg`, plus the block to
paste, `data/figures/myst/<id>.myst.txt`.

## 5. Fix every `LINT:` line

The lint is not advisory. Common ones and what they mean:

| Line | What to do |
|---|---|
| `a label that states a number needs cite:` | add `cite:`, or take the number out of the label |
| `cite key [^x] is not defined on <page>` | you used a key the page does not have; use one it does, or drop the claim |
| `cite key [^x] is a patent shown as in force` | remove it; see above |
| `a value that is not public must say 'not public' first` | reword the note |
| `text escapes the canvas margins` | the title or note is too long; shorten it |
| `text overlap` | two labels collided; shorten a note or move a callout's `x` |
| `leader of … touches text` / `leaders cross` | move the anchor (`x`) of a callout or dimension |
| `leader … runs within 5 u of a material edge` | the riser looks like a film; move the callout's `x` away from the wall |
| `more than two top-routed labels in panel N` | you have more than two `dims` + `callouts`; drop one |
| `text inside a drawing area` | a cross-section never has text on the drawing; use a label |

## 6. Look at it

This is not optional, and the lint does not replace it.

```
uv run python tools/gen_figures.py harness <id>
uv run -q --with pillow python tools/shoot.py "file://$PWD/tmp/figures/qa/light-desktop.html" tmp/shots/<id>-ld
uv run -q --with pillow python tools/shoot.py "file://$PWD/tmp/figures/qa/light-phone.html"   tmp/shots/<id>-lp --width 400
uv run -q --with pillow python tools/shoot.py "file://$PWD/tmp/figures/qa/dark-desktop.html"  tmp/shots/<id>-dd
uv run -q --with pillow python tools/shoot.py "file://$PWD/tmp/figures/qa/dark-phone.html"    tmp/shots/<id>-dp --width 400
```

Open every PNG with the Read tool and check:

1. Every label is readable at phone width, and every label is beside the thing it names.
2. No leader looks like a layer, and no leader runs through a label.
3. Nothing escapes its box and nothing is clipped at an edge.
4. The accent-coloured highlight is on **the one thing this step changed**, and on nothing
   else.
5. The dark version keeps every boundary visible and its ground matches the page.
6. The before and after panels line up: a feature is at the same x in both.
7. The picture actually agrees with the sentence above it on the page.

Iterate until it is genuinely good. Record in your progress file, per figure, what you
checked and any compromise you accepted.

## 7. Paste it into the page

Paste `data/figures/myst/<id>.myst.txt` **whole and unchanged** after the first paragraph
of "What this step is" (a step page). Never edit the block in the page: `--check` compares
it with the generated one and fails if they differ.

**A figure never replaces text.** Nothing is deleted because a drawing now shows it. The
only change to the page is the added block, and `git diff` must show only additions.

## 8. Before you finish

```
uv run python tools/gen_figures.py --check
uv run python tools/check_refs.py
uv run python tools/check_inforce.py
uv run sphinx-build -W -q -b html docs tmp/_build/html
```

Then shoot the real built page, not just the harness, at both widths, and look at it once
more in place.

## The other kinds

* `kind: flowmap` — the module strip on the overview. Data only: modules, step ranges,
  masks, phases.
* `kind: stack` — a layer chart **to scale**, with an axis. Every thickness must be a
  public, cited number: the lint refuses a layer whose `basis` is anything else, and the
  caption must say "To scale".
* `kind: chain` — vertical boxes joined by arrows, with an optional side branch per node
  (machine block-chains, mask derivation chains). Text sits inside the boxes here; that is
  the one place it may.

## Things that are always wrong

* Writing or editing SVG by hand.
* A number in a figure that the target page does not give, or gives with a different
  hedge, a different unit or a different number of significant figures.
* A citation key that is not defined on the target page.
* Drawing a value that is not public to scale, or without saying it is not public.
* Anything from a patent shown as in force.
* Deleting or rewriting page text because the figure now shows it.
* A figure inside a `{dropdown}`.
* `{numref}`: `numfig` is off and the `-W` build fails.
